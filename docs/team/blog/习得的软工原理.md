# 习得的软工原理 / 方法 / 技能

> 对应 Alpha 冲刺（10/21 – 11/02）。每条都尽量写上项目里的具体例子，而不是只写概念。

## 一、敏捷与 Scrum

- **Sprint 与 User Story**：把需求拆成带验收标准的用户故事（US-xx），按冲刺排期；S1 共 11 个故事、55 故事点。
- **Issue 驱动开发**：每个故事对应 GitHub Issue，状态靠 Projects 看板拖动沉淀，替代每日站会；卡点在 Issue 评论里升级。
- **迭代评审**：每个迭代末用「燃尽图 + 演示 + 测试报告」回答三个问题：做完了什么、没做完为什么、下个迭代改什么。
- **燃尽图**：用剩余故事数衡量进度。本冲刺 S1 共 11 故事，第六周末（10/31）完成 1（US-02），剩余 10。图要按真实关闭日期画，不能为了让曲线好看提前记完成。

## 二、API-First 与契约先行

- 先定 `openapi.yaml` 接口契约，前后端并行：前端用 mock 数据先行开发，后端按契约实现，最后对接。降低耦合、提前暴露接口分歧。
- 契约不是写完就算：算法服务用一条测试直接比对 `openapi.yaml` 与 FastAPI 生成的 schema（字段、必填、长度、响应结构），契约漂移会立刻让 CI 变红。
- 教训：M5 的 ER 图与契约迟迟未定稿，M3 的页面开发被真实阻塞——**契约是团队级依赖，应该第一个交付**，而不是最后补。

## 三、CI/CD 与自动化质量门禁

- **GitHub Actions** 在每次 PR 自动跑：`guard`（敏感文件/大文件/提交信息）、`changes`（按目录选择模块）、`algo`（Ruff + Pytest + 覆盖率）、`api-server`（Maven verify）、`stack`（Docker 全栈 + 真实 HTTP 冒烟）、`quality`（汇总结果）。
- **踩坑**：GitHub 合并 PR 时会生成自动合并提交，`git log origin/develop..HEAD` 因此总含合并节点，`guard` 会把它们判成不合规提交而永久失败。修复：过滤 `--no-merges`。
- **质量门禁要选「一定会出结果」的检查**：只保留按目录触发的 job 时，改 README 的 PR 一条检查都不会跑，分支保护反而卡死。所以保留一个无条件运行的 `guard`。
- **门禁的意义**：本周 M4 的 PR#43 缺 `package.json`、M5 的 PR#47 误改 Java 21，都是 CI 先发现而不是靠人肉 review 发现。

## 四、分支策略与协作

- `feature/*` / `docs/*` 分支开发 → 提 PR → 至少 1 次非作者评审 → 合入 `develop`；禁止直推主干。
- **合并方式按场景选**：单提交的小改动用 squash 更干净；像 PR#49 这种 21 个小提交、需要保留演进过程的，用 merge commit 保留历史，方便按提交回滚。
- **没有 review 的合入等于没有质量记录**：PR#49 先转正草稿、再由非作者 approve，审核意见里写清「测了什么、没测什么」，事后可追溯。
- **分支保护 + CODEOWNERS**：限制直接推送、明确代码属主；`dismiss_stale_reviews` 会让 approve 后新增的提交重新走评审，避免「批完再改」。

## 五、Mock 驱动开发

- 依赖（后端/ER 图）未就绪时，前端先用写死数据推进界面与交互，待契约定稿再替换，避免全员阻塞。
- Mock 必须标清楚：管理端三个页面在文档里明确写「mock 演示」，不能当成已经联调。

## 六、架构分层

- 前端（小程序）/ 管理端（Vue3）/ 后端（Spring Boot）/ 算法（FastAPI）/ 契约（openapi）分层，各自独立子目录，职责清晰、便于并行。
- 新增的算法服务通过 HTTP 被后端调用，而不是把词库逻辑塞进 Java——**把变化快的策略（词库、等级）放在独立服务里**，改词库不用重新发布后端。

## 七、测试与出口条件

- 测试不仅验证功能，还包括 Bug List、场景测试、动态出口条件（随 Deadline 与风险调整范围）。
- **测试数字要说清楚口径**：141 项自动化测试（101 Python + 40 Java）覆盖的是算法、客户端和编排，不等于 80 条业务用例已执行。
- **覆盖率是下限不是目标**：算法服务 98.07% 的语句/分支覆盖率说明分支被走到，但不说明业务规则正确，规则正确性仍要靠独立标注集评估。

## 八、失败关闭（Fail-closed）

- 依赖不可用时，安全相关的调用应**宁可拒绝也不放行**：审核服务超时、返回非 2xx、字段缺失或判定自相矛盾时，Java 客户端统一返回 503，业务不得写库。
- 反例思考：如果超时就「默认通过」，攻击者只要打挂审核服务就能绕过内容审核。失败关闭把可用性问题降级为业务不可写，而不是安全问题。
- 代价也要接受：审核服务抖动会直接影响发布成功率，所以要有超时（2s 连接 / 3s 读取）、重试策略和监控，而不是无限等待。

## 九、边界防御与输入校验

- 只靠网关限制请求体不够：直连容器、分块传输（chunked）、伪造 `Content-Length` 都能绕过 Nginx。服务自身必须再设一道 16KiB 上限，并且**先看长度头、再边读边计数**。
- 拒绝时不回显输入：参数校验失败统一返回 `{"detail": "Invalid request"}`，避免把用户原文（可能含手机号、学号）写进响应和日志。
- 阈值要测边界：16384 通过、16385 拒绝、`Content-Length: 00001` 不能绕过、声明 1 字节实际发 20KB 仍要拒绝。

## 十、隐私最小化与可观测性

- **只收集必要字段**：匿名 ID 用 HMAC（密钥 + 用途 + 内部用户 ID）生成，同一用户在不同场景得到不同假名，避免用学号直接当主键。
- **日志默认可能泄露**：请求体、Authorization 头、异常堆栈都可能带凭证。Logback 用自定义 converter 对整行输出做脱敏，而不是只处理 message。
- **脱敏有代价**：正则会把 8–20 位连续数字一律打码，可能连 traceId、耗时一起隐藏——安全和可排查性要权衡，规则需要 review。
- **扫描工具输出位置而不是原值**：PII 扫描只报文件序号、行号和规则名，不打印匹配内容，报告本身不会成为新的泄露源。

## 十一、小步提交与可回滚

- PR#49 拆成 21 个提交，单个最大约 90 行，按「接口 → 实现 → 测试 → 文档」推进；出问题时可以只 revert 一个提交。
- 提交信息用 `<类型>(<范围>): <描述>`，让 `git log` 本身成为变更说明；`guard` 会拦截不合规的标题。
- 每个 PR 描述都写「影响面与回滚」，尤其是配置类改动（数据库名、端口、容器命名）——这类改动代码不一定报错，但会让队友的本地环境失效。

## 十二、文档与诚实性

- 文档要区分「已实现」「已验证」「已验收」三件事；本周的进展文档逐条标注了哪些是骨架、哪些未执行。
- 不要把「测试通过」写成「功能完成」：算法单测通过只说明代码分支正确，不代表树洞发布链路已经接好。
- 也不要为了好看删掉「未完成」「不能证明」这类句子——它们是团队在答辩和抽查时的保护，而不是减分项。
