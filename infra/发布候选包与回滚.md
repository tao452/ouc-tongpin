# 发布候选包与回滚操作

四条工作流为 ci、deploy-test、release、nightly，文件均在 `.github/workflows/`。

## 临时测试部署

deploy-test 支持手动运行，也被 PR CI 复用。它在独立 GitHub runner 上构建并启动五个服务，
检查健康状态、HTTP 路由和用例结果，上传 `catalogue-stack-evidence`，最后清理容器和测试数据卷。
这个环境用于自动验证，任务结束即回收，不提供长期访问地址。

## 发布候选包

release 在 PR 上自动构建候选包，手动运行时默认也只构建候选包。
步骤为 Java 17 测试和构建、Python 测试、Node 22 管理端构建、归档、SHA256 校验。
Actions 产物 `release-candidate` 包含：

- `deployment-source.tar.gz`：来自该次 Git 提交的完整跟踪文件，用于重新构建镜像。
- `api-server.jar`：已构建 Java 服务。
- `admin-web.tar.gz`：已构建管理端静态文件。
- `manifest.json`：来源提交、运行版本、文件大小和 SHA256。
- `SHA256SUMS`：候选包文件的校验和。

产物不包含本地 `.env` 和 `qa-private` 数据。校验代码拒绝不安全归档路径、链接和敏感目录。
下载并解压 Actions 产物后，在仓库中执行：

```powershell
python scripts/release/package_candidate.py --output 候选包目录 --verify-only
```

## GitHub Release 发布

正式发布由成员手动运行 release 并选择 publish。前置检查依次要求：

1. 运行引用为已存在的 `vX.Y.Z` tag。
2. tag 指向当前 main 提交，来源提交与候选包一致。
3. 该提交最新 quality 检查成功。
4. 候选包哈希与来源归档校验通过。

发布过程先建 Draft Release、上传全部文件，再公开 Release。上传中断时保留 Draft 便于检查。
本轮执行候选包构建，未创建正式版本 tag 或公开 Release。

## 长期测试环境接入

资源交付包括 Linux 主机、Docker Compose v2、域名、网络入口、部署账号和受限凭证渠道。
组长分配主机与域名，M5 配合数据库与业务配置，M6 按候选包部署并记录访问与回滚结果。
本轮先使用 GitHub 临时环境，独立测试服务器未部署。

## 保留数据的回滚

首次部署起固定 Compose project name，例如 `tongpin-test`，并将环境变量文件保存在版本目录之外。
每次部署保存当前候选包 manifest 和前一候选包。需要回滚时使用前一包的源代码及同一配置：

```bash
docker compose --project-name tongpin-test --env-file /srv/tongpin/config/test.env -f infra/docker-compose.yml up -d --build --wait --wait-timeout 240
python scripts/e2e/foundation-smoke.py
```

该命令在前一版本解压目录中执行，固定 project name 使数据卷保持一致。常规停止使用 `down`，保留数据卷。
数据库迁移必须另有兼容性方案；当前候选包没有数据库迁移。长期环境的版本切换演练随服务器部署执行。
